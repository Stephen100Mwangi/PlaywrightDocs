# Writing Tests

Tests are written to
1. perform actions 
2. assert the state against expectations

Playwright test waits for actionability checks to pass before performing an action
- no need for manual waits or dealing with race conditions

## Structure of a test file
```
import {test, expect} from '@playwright/test'

// test('description',()=>{})
- Description of the test being performed
- anonymous function to 
1. Perform actions
2. Validate assertions

test('login page',()=>{
    await page.goto('https://example.demo');

    await expect(page).toHaveTitle('Login');
})
```

:Note: When using JS, add `//@ts-check` at the start of each test file to perform automatic type checking

### Actions
1. Navigation - URL `await page.goto('https://example.demo')`
2. Interaction - Starts by locating an element. Interact with the elements by clciking, checking, unchecking, hovering

### Assertions
- Validating an expected state

1. Matchers
`expect(value).matcher()`

Playwright provides async matchers that wait until the expected condition is met
- Ensures tests are non-flaky and resilient

2. Generic matchers 
- Include `toBeTruthy`, `toEqual`, `toContain`
- Do not use await keyword as they perform immediate synchronous checks on already available values

## Test Isolation
Playwright tests are built around the concept of test fixtures
Pages are isolated between tests due to browser context which acts like a new browser profile

## Test Hooks
`test.describe()` - Group related tests
`test.beforeEach` - Run before each test
`test.afterEach` - Run after each test
`test.beforeAll` - Run before all tests
`test.afterAll` - Run after all tests

Playwright tests are built on async/await semantics:

Actions → return promises
Assertions → retry automatically
Test runner → relies on awaited steps for correctness

Auto‑waiting removes manual waits, not await.

await is not about waiting for the element.
It’s about waiting for the JavaScript Promise to finish.
